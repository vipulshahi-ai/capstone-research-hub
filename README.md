# My Capstone Guide research workflow

The public GitHub Pages portal loads and saves records through the existing Apps Script web app. A team access code is required for team reads and writes. Codes are generated by `setupResearchWorkflow`, stored in Script Properties, and listed in the guide's `Portal Access` sheet. A separate `GUIDE_READ_CODE` Script Property can enable a read-only guide view across the listed projects. It must never be committed to this repository or placed in the public page. Keep the tracker restricted to guides; distribute only each team's own code. Codes identify a team, not an authenticated individual. The selected student is a self-reported contributor.

## Student workflow

1. Select the project, enter its code and load shared records.
2. Record the problem, motivation, question, measurable objectives, scope and shared Drive folder.
3. Use the Scholar link to search manually. Save queries, dates and search notes.
4. Check title and abstract before downloading. Record source metadata, venue, include/exclude reason and legal source link. Link a permitted Drive PDF after upload.
5. Open included papers in the review form. Record task, algorithm, dataset, metrics, contextual results, limitations and relevance/gap. Mark Complete only after reading and checking the source.
6. Compare studies in the synthesis form and cite the supporting Paper IDs. Ask the guide to approve the problem, review and gap in Sheets.
7. Each student submits a methodology as an **Individual Draft**. Once both drafts are guide-approved, discuss their differences and submit one new **Final Team Version**. Explain what was retained or changed from each draft. Only a final-team record with **Final Team Approval = Approved** is the team's agreed method.

Each team targets 30 journal and 10 conference papers. Each student targets 15 journals and 5 conferences. Excluded papers do not count. Reading and Complete are separate from screening. A Drive link is recorded, not proof of a file's permissions or licence. The portal does not scrape Scholar, download papers or change Drive sharing automatically.

## Records

- Existing Papers and Literature Review tabs are extended by header name; their existing columns and validations remain.
- Research Problems, Search Log and Research Gaps contain the new form records.
- Interactions retains the existing guide-meeting records.
- Portal Audit records successful mutations with record ID, owner, timestamp and revision.
- Methodology preserves individual drafts and one consolidated final-team record per project. The final record stores both contributors, source draft IDs, comparison notes and its first submission timestamp. An approved final record cannot be overwritten by students.
- Existing team views remain; portal records are filtered by the authorized project on the server and displayed as expandable cards.
- Shared data is loaded into memory; form drafts are saved locally. Old v2 browser records are preserved and paper drafts can be opened for manual migration.

Saving waits for a readable successful server response. A timeout/error retains the draft and does not claim success. Retrying identical content is idempotent; stale edits are rejected rather than overwriting newer team work. Reload shared records and open the latest record to resolve a conflict. The portal shows guide approval status and feedback. Students open a red entry, correct it, and save to resubmit; student changes reset approval to Pending. The guide continues to approve or return entries from the restricted spreadsheet.

For Methodology, the guide reviews individual drafts in **Guide Approval** and the consolidated record in **Final Team Approval**. Record comparison and revision feedback in **Guide Feedback**. Do not mark two individual drafts as the final method; their approvals indicate that each is suitable input to the consolidation. Use **First Submitted At** and Portal Audit when checking the 14 October deadline; a later revision date does not erase an on-time first submission. Timeliness informs grading only according to the university rubric and documented contribution, not an automatic portal score.

## Deployment and checks

The live repository currently publishes its root through GitHub Pages. Keep `index.html`, `research.js`, `styles.css` and `config.js` in the published root. The local Actions workflow also includes `research.js` if deployment later switches to Actions.

Paste `Code.gs` into the existing bound Apps Script project, run `setupResearchWorkflow`, and update the existing web-app deployment to a new version. This retains the endpoint and spreadsheet ID. Do not commit team access codes. `node --test tests/render-records.test.cjs` checks the expandable record views without writing live records.

To enable guide browsing, set `GUIDE_READ_CODE` in Apps Script **Project Settings → Script Properties**, then deploy a new web-app version. Enter that key in the portal's access field and select any project. The key stays in browser memory only until the page is closed or **Lock session** is pressed. The server rejects all save actions with it; approval and feedback remain guide-only edits in Sheets. A short numeric key is easier to guess and should be replaced with a long private passphrase when practical.

Faculty milestone dates: 7 Oct problem/literature, 14 Oct methodology, 10 Nov results, 25 Nov first draft, 5 Dec viva/TRL/submission status. The current forms cover research, literature, methodology and guide interactions; later milestones remain a timeline, not implemented submission forms.
